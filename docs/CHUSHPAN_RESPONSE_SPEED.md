# Ускорение отклика — 3 ноября 2026

Рабочий код изменён поверх существующих Conversation, ControlSession, реестра
инструментов, SQLite, Ollama/Gemini и потока Silero. Сценарии и выбор одной
версии по местоположению сохранены. Личные настройки не переписывались.

## Что измерено

Исходная версия: `9c3d24a`. До изменения рабочего тракта сохранены 30 обращений:
10 фиксированных случаев × 3 повтора. После изменений повторён тот же корпус.
Процесс последовательно использует один клиент Ollama и один голос Silero.
Прогрев вынесен из времени обращения и сохранён отдельно. Температура 0,6;
qwen3:8b, окно 16384, keep_alive 30m, Silero eugene. Никаких загрузок моделей.

Это реальная генерация локальной модели и PCM, но инструменты подменены
стендом. Микрофон и аудиовыход не открывались. Отсчёт начинается с готового
текста запроса. `first_pcm_ready_s` означает готовность первого содержательного
аудиофрагмента, а не слышимый звук и не конец речи пользователя.
Фразы ожидания в этот показатель не входят. Экспорт находится в игнорируемом
`data/latency-benchmarks/`, вне Git; сохранённые пользовательские разговоры
для этого корпуса не используются.

Для четырёх типов вопросов к LLM (разговор, объяснение, контекстное уточнение,
длинный ответ), всего 12 обращений:

- p50: **7,678 → 0,915 с**; среднее: **9,974 → 1,173 с**.
- p95 и максимум: **31,235 → 4,588 с**. При таком небольшом числе образцов
  p95 совпадает с максимумом; это не оценка всей будущей голосовой нагрузки.
- До: 11 завершённых измерений и одна ошибка TTS после первого фрагмента.
  После: 12 завершённых измерений, ошибок и отмен нет.
- Холодный первый вопрос всё ещё требует 4,588 с. Цель 1–3 с не достигнута
  для каждого запроса; гарантии полного голосового отклика <3 с нет.

По типам, медиана до первого PCM:

- Разговор: 6,973 → 0,841 с.
- Объяснение: 7,867 → 1,005 с.
- Контекст: 15,572 → 0,548 с.
- Длинный ответ: 7,355 → 0,543 с; до успешны 2 из 3, после 3 из 3.
- Относительная громкость: 5,464 → 0,023 с; до один тайм-аут 90 с.
- Safari: 4,593 → 0,022 с.
- Составная LED + MacBook: раньше все три запроса требовали уточнения,
  теперь оба действия разобраны и переданы стенду без LLM; p50 0,023 с.
- Пользовательский сценарий уже выполнялся локально: 0,030 → 0,029 с.
  Подсветка и её прежний маршрут числовой яркости тоже уже были быстрыми.
  Неопределённая «Яркость на 50 процентов» сохраняет существующее значение
  яркости ленты; для экрана явно указывается MacBook/экран.

Весь смешанный корпус: p50 4,593 → 0,028 с, p95 15,572 → 1,471 с,
среднее 5,352 → 0,484 с, максимум 31,235 → 4,588 с. До измерено 25 из 30:
2 ошибки, 3 отклонения. После 30 из 30. Малые времена команд относятся только
к стенду, без VAD/STT/устройств/аудиовыхода. Их нельзя выдавать за реальный
голосовой отклик или прибавлять к ним чужие медианы и объявлять результат замером.

Проверка STT: 5 синтетических фраз Silero × 3 повтора, тот же локальный
Whisper large-v3-turbo из кэша, без сети. Все 15 распознаваний соответствуют
смыслу исходных фраз; команды попадают в нужные маршруты. Время 0,480–0,499 с.
Это контроль синтетической речи, а не доказательство качества живой речи,
акцентов, шума или акустики комнаты. STT-модель и её фильтры не заменены.

## Причины задержек и изменения

В прочитанном снимке существующей статистики (1906 трасс, включая активации)
медиана первого текста LLM — около 11,98 с; обдумывание Ollama — 8,36 с.
STT — 0,545 с, генерация TTS — 0,040 с, подготовка памяти — 0,0019 с.
Это исторические этапы с разным числом образцов, не одна сквозная трасса.

Три главные причины: лишние LLM-запросы для действий, hidden thinking на
обычных объяснениях и несколько облачных ожиданий перед локальным резервом.

- Локальная грамматика расширена в существующем ControlSession: громкость
  вверх/вниз от фактического уровня, проценты цифрами и словами, приложения
  по точному известному имени/русскому псевдониму, MacBook в составных командах.
  Неизвестная часть составной команды не выполняется частично. Короткая
  корректировка громкости привязана к устройству, разговору и сроку действия.
  Все действия проходят тот же реестр, schema/capability/agent/permission
  checks. Точный grant плана не отменяет пользовательский intent-veto инструмента.
- Обычные объяснения и контекстные вопросы используют небольшой текстовый
  системный промпт без схем действий и без скрытого рассуждения. Математика,
  код, анализ, сложное планирование, актуальные и ответственные вопросы
  сохраняют полный маршрут. `think_for_simple=true` возвращает thinking.
  Классификация не предоставляет полномочий на действия.
- Неизменяемая часть промпта стабильна; повтор инструкции характера убран.
  Полная SQLite-история сохранена. Для локальной длинной истории добавлены
  ограниченные извлечённые цитаты старых реплик; никаких выдуманных сводок
  и дополнительных запросов модели. Облачный объём экспорта не расширен.
- Ожидание первого результата облачной цепочки ограничено общим бюджетом
  `first_result_budget_s=8`, для обычного текста `simple_timeout_s=3`.
  Это верхние границы ожидания **до локальной генерации**, а не обещание
  ответа за 3 с. Существующие меньшие тайм-ауты сохраняются. Выбранная
  настроенная резервная Gemini используется сразу для обычных вопросов.
  Подписанные ходы инструментов сохраняют провайдера и полный бюджет;
  после частичного результата нет повторного выполнения через fallback.
- Поток текста → смысловые фрагменты → Silero → очередь вывода уже существовал.
  Он сохранён, добавлена обратная связь очереди: не более двух готовых
  предложений вперёд. Синтез следующего фрагмента перекрывает воспроизведение.
  Отмена дожидается остановки фонового сетевого насоса; отменённый синтез
  не добавляет аудио в очередь. Отдельно измеряется подготовка произношения.
- VAD сохраняет установленный пользователем нижний предел тишины и тихие
  окончания через hysteresis. Для длинной/паузной речи адаптивно увеличивает
  запас, максимум до 1,1 с. Это улучшение сохранности фразы, а не искусственное
  сокращение паузы ради цифр. Шум, паузы и длинные команды проверяются тестами.

Голос в реальной конфигурации — **Silero eugene**, а не qwen3-tts-mlx.
Голос, произношение, AEC и вывод на выбранное устройство сохранены. Успешный
запрос macOS на открытие приложения обозначает отправку запроса; физические
состояния LED не объявляются подтверждёнными после одной записи BLE.
Относительная громкость требует чтения текущего и проверки итогового уровня.
Shortcuts, BetterDisplay, Bluetooth и физические сценарии не запускались.

## Сравнение конфигураций

- qwen3:8b, 16K, выборочное отключение thinking: итоговый p50 LLM-корпуса
  0,915 с; первое промежуточное повторение — 0,775 с. Разброс не скрывается.
- Та же 8B, 8K: p50 0,830 с, среднее 1,160 с, максимум 4,618 с.
  Достоверного выигрыша над 16K на коротких вопросах нет. Окно не уменьшено:
  сложным вопросам и инструментам нужен запас.
- Уже установленная qwen3:4b, 16K: p50 первого PCM 0,775 с, но медиана
  полной генерации **38,628 с**, отдельные короткие запросы 51–72 с.
  Быстрое начало скрывает чрезмерную длину. Модель не заменена; экспериментальная
  4B выгружена из памяти после измерений. Новые модели не скачивались.
- Холодная загрузка 8B: 3,593 с до, 2,823 с в итоговом прогоне после.
  Прогрев голоса: 2,303 и 2,112 с. Эти значения не входят в onset.
  В обычном голосовом процессе keep_alive продолжает определяться текущим
  профилем ресурсов (balanced — 15m); настройки экономии не отключены.

Новых запросов к Gemini не выполнялось: нет новых расходов и нет заявления
об измеренном ускорении живой сети. SDK уже передаёт текст потоком. Добавлены
измерения первого события и полного потока; первое событие объединяет сеть
и ожидание сервера, не называется чистым RTT. Тайм-ауты, rate limit, недоступность,
переход на Ollama и запрет повторов проверены SDK-моками.

Параметры проверены по первичным источникам:
[Ollama API](https://github.com/ollama/ollama/blob/main/docs/api.md),
[Gemini thinking](https://ai.google.dev/gemini-api/docs/thinking).

## Статистика и воспроизведение проверки

В существующей статистике появились вид ввода, маршрут и тип запроса,
размер контекста, скорость токенов, причина fallback, сравнение ревизий,
ошибки/отмены/незавершённые/отклонённые запросы. Время полного ответа с озвучкой
показано отдельно от первого содержательного звука. Контрольные PCM-замеры
показаны отдельной секцией и не попадают в реальные voice-метрики.

Повторять на одной машине, без параллельной нагрузки, до изменения кода с
`--label before`, после — с `--label after`. Метка не откатывает код.

```bash
.venv/bin/python -m backend.bench_response --label before --runs 3
.venv/bin/python -m backend.bench_response --label after --runs 3
.venv/bin/python -m backend.bench_response --label sample --runs 3 --num-ctx 8192 --cases dialogue explanation context long_answer
.venv/bin/python -m backend.bench_response --label sample --runs 3 --model qwen3:4b --cases dialogue explanation context long_answer
HF_HUB_OFFLINE=1 .venv/bin/python -m backend.bench_response --label sample --runs 3 --stt
```

Команды используют только локальные модели и синтез в RAM, подменяют реальные
интеграции, не открывают микрофон, плеер или системный `say`. Облачных запросов
нет. Для STT требуется уже заполненный локальный кэш. Вопросы ошибок устройств
и недоступности облака проверяются детерминированными регрессионными тестами,
а не живыми устройствами. Новая статистика появляется после перезапуска
обычного приложения; автоматический перезапуск с микрофоном в этой работе
не выполнялся.

Итоговая проверка: 1761 backend-тест, 49 frontend-тестов, Ruff check,
Ruff format --check, TypeScript/Vite build и git diff --check прошли.
Панель статистики проверена в локальном браузере с реальными агрегатами
контрольных прогонов; ошибок консоли нет. Тесты отдельно проверяют первый
фрагмент до завершения модели, порядок/отмену озвучки, ограничение очереди,
публикацию worker-таймингов только из потока event loop, неизменность памяти,
ошибки устройств и безопасное переключение провайдеров.
