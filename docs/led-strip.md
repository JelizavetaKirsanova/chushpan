# Bluetooth LED-лента Чушпана

Модуль `backend/led.py` управляет ELK-BLEDOB локально через Bleak и CoreBluetooth.
Облачные API и приложение производителя для управления не нужны. Приложение
на телефоне лучше закрыть перед подключением с Mac.

## Установка и настройки

Из корня `my-jarvis`:

```sh
uv sync --locked
uv run python -m backend led status
uv run python -m backend led inspect
uv run python -m backend led discover
```

`status` читает только локальный журнал, не подключается и не показывает текущее
физическое состояние. `inspect` подключается, проверяет GATT и до двух секунд
слушает FFF4; управляющих пакетов не отправляет. Неизвестные уведомления не
интерпретируются как подтверждение исполнения.

В `config.yaml`, секция `led`, сохранены имя ELK-BLEDOB, идентификатор прошивки
JSY-P10A27NM-V1.1.2 и macOS UUID `3A4F5301-2291-2E56-628D-83567E951876`.
Service — FFF0, write — FFF3, notify — FFF4, все с окончанием
`-0000-1000-8000-00805f9b34fb`. Запись всегда `response=False`.

`enabled: false` отключает модуль. `night_off: false` отключает только ночной шаг.
При изменении настроек перезапустите Чушпана. Обновлённый `.app` должен быть
собран существующим механизмом проекта: `backend.app_bundle.build(settings)`
добавляет `NSBluetoothAlwaysUsageDescription`. Для уже установленного автозапуска
можно повторить `uv run python -m backend autostart install` с прежними флагами.
macOS может запросить доступ к Bluetooth. Если доступ запрещён, откройте
«Системные настройки → Конфиденциальность и безопасность → Bluetooth» и разрешите
его приложению, из которого запускается Python, или Чушпану при запуске из `.app`.
UUID относится к этому Mac; при переносе на другой Mac его потребуется заменить.
`discover` в течение четырёх секунд ищет все видимые BLE-устройства без фильтра
рекламируемых сервисов и точного имени. ELK-BLEDOB, ELK-BLEDDM и семейство ELK-BLE,
а также устройства с рекламируемым FFF0 помечаются кандидатами; остальные остаются
неизвестными. Имя и сервис не подтверждают протокол. Записи и автоматической
перепривязки нет. Новые ленты удобнее добавлять через «Устройства → Найти устройства»:
там видны RSSI, неизвестные устройства и проверка подключения без команд.
Ручная замена `led.address` нужна только для конфигурации основной CLI-ленты.
Отсутствие старого UUID не вызывает перебор команд или выбор другого устройства.

Порядок подключения, ограничения и автоматические проверки описаны в
[BLE_DISCOVERY_FIX.md](BLE_DISCOVERY_FIX.md).

Подтверждённые возможности, идентичность устройства, последний запрос и
результат записи сохраняются в `data/led/device.json` (или в выбранном `data_dir`).
Файл исключён из Git вместе с `data/`. Запись атомарная; блокировка защищает
от одновременного управления из голоса и CLI. При изменении UUID, идентификатора
прошивки или GATT-профиля в настройках подтверждения сбрасываются. Прошивка
устройства автоматически не считывается. Повреждённый файл блокирует запись.

## Формат и ручная проверка

Подтверждённый пользователем красный пакет:
`7E 07 05 03 FF 00 00 10 EF`. RGB формируется как
`7E 07 05 03 RR GG BB 10 EF`, без перестановки каналов и вычисления checksum.

Для питания исследована семья пакетов:

- Включение: `7E 04 04 01 00 01 FF 00 EF`.
- Выключение: `7E 04 04 00 00 00 FF 00 EF`.
- Яркость: `7E 04 01 VV FF FF FF 00 EF`, VV — целое 0–100, не 0–255.

Источники для исследования: [оригинальная реализация CommandUtils.kt](https://github.com/user154lt/ELK-BLEDOM-Command-Util/blob/master/CommandUtils.kt),
[Bleak: подключение и запись](https://bleak.readthedocs.io/en/stable/api/client.html),
[особенности macOS и разрешений](https://bleak.readthedocs.io/en/stable/backends/macos.html).
Пакеты из сторонних реализаций первоначально считаются кандидатами, а не
подтверждением совместимости именно этой прошивки.

На чистом локальном профиле разрешён только исходный красный. Голос, LLM и
ночной сценарий не могут включить экспериментальный режим. Отдельная команда
`probe` показывает точный пакет, требует ввести `ОТПРАВИТЬ`, отправляет один пакет
и затем просит ввести `ДА`, только если результат действительно виден на ленте.
Без этого режим не разрешается. Отрицательный ответ отзывает подтверждение.
Проверки красного, зелёного и синего вместе разрешают весь формат RGB;
успешная визуальная проверка яркости разрешает диапазон 0–100. Это проверка
формата, а не измерение каждого оттенка или абсолютной световой мощности.

```sh
uv run python -m backend led probe "сделай подсветку зелёной"
uv run python -m backend led probe "сделай подсветку синей"
uv run python -m backend led probe "выключи подсветку"
uv run python -m backend led probe "включи подсветку"
uv run python -m backend led probe "установи яркость подсветки 25%"
```

В этой сессии 1 ноября 2026 года пользователь визуально подтвердил синий,
зелёный, скорректированные фиолетовый, розовый, светло-розовый и тёплый белый,
выключение, включение и яркость 25% и 100%.
Исходный красный
был подтверждён до начала работы. Эти результаты сохранены в локальном профиле.
Первая запись синего сразу перед отключением не изменила цвет. Повторная запись
с паузами сработала. Причину нельзя однозначно установить по этому наблюдению;
модуль теперь выдерживает паузы после подключения и записи (`settle_s: 1`).

## Проверка обычного управления

Каждую текстовую команду можно выполнить без микрофона:

```sh
uv run python -m backend led command "сделай подсветку красной"
```

Для голоса сначала обратитесь «Чушпан». В активной диалоговой сессии уверенно
распознанные команды ленты можно продолжать без имени, если не включён строгий
режим обязательного обращения. Эхо, низкая уверенность STT и закрытая сессия
не дают такого разрешения. Текстовые команды используют тот же защищённый путь
`local_commands → ToolRegistry → LocalMacAgent`, без Gemini или Ollama.
Проверяются авторизованная сессия, `mac.system`, доступный Mac Agent и совпадение
нормализованного намерения с исходной просьбой. Подтверждение кода для обычной
разрешённой LED-команды не требуется; проверки опасных действий не изменены.

Примеры: «Ленту розовый», «Включи розовый на ленте», «Включи мне розовый на
лет ленте», «Сделаем мою ленту розовой», «Хочу розовую подсветку», «Поставь
светло-розовый», «Поставь тёплый белый», «Включи ленту», «Выключи подсветку»,
«Яркость 30 процентов», «Сделай ленту на 30%», «Сделай мне на ленте 30% яркости»,
«Убавь яркость», «Сделай поярче». `LED`, «лед» и «лет» распознаются как варианты
имени настроенной ленты. Остальные непонятные слова не удаляются молча.

В коротких просьбах о цвете, «Яркость 30 процентов» и «Сделай поярче» устройством
по умолчанию является разрешённая LED-лента. Существующее «Установи яркость 25%»
сохраняет значение яркости Mac; для однозначности говорите «яркость ленты» или
«яркость экрана». Относительная яркость меняет последнее записанное значение
на 10 процентных пунктов; если оно неизвестно, требуется сначала абсолютное
значение. Это не измерение физической яркости.

До трёх известных действий одной ленты можно объединить через «и», например
«Включи ленту на белый цвет и сделай яркость 100%». Сначала разбирается вся
просьба. Разные устройства, отрицания, цитаты и неоднозначные альтернативы
не исполняются; после ошибки следующая запись не запускается, а уже сделанные
записи явно отмечаются. Неопознанная прямая просьба о ленте получает локальное
уточнение с поддерживаемыми примерами, а не выдуманную LLM команду.

После предложения «Сделать ленту розовой?» короткое «Да» выполняет именно это
действие один раз в течение двух минут. Список плейлистов и существующий Favourite
Songs сохраняют прежний контекст предложения и проверку реального API. «Да»
не заменяет код подтверждения опасных действий.

Диагностика `LED_STAGE` содержит request ID, этап, структурированное намерение и
состояние отправки без расшифровок речи, ключей или BLE UUID. Те же этапы видны
в постоянных трассах: STT, нормализация, намерение, выбор инструмента, разрешение,
подключение, запись, результат и ответ. Полные очищенные результаты инструментов
и исходная реплика сохраняются в существующей истории разговора.

Проверьте режимы по одному:

1. **RGB и названия цветов.** «Чушпан, сделай подсветку красной», затем синей,
   фиолетовой, розовой; «Чушпан, сделай цвет подсветки тёплый белый». Можно сказать
   «включи фиолетовую подсветку» или задать `RGB 12 34 56`.
   Красный — (255,0,0), синий — (0,0,255), фиолетовый — (255,0,200), розовый —
   (255,0,32), светло-розовый — (255,16,32), тёплый белый — (255,48,32).
   Светло-розовый поддерживает написание с дефисом и без: «сделай подсветку
   светло-розовой», «сделай подсветку светло розовой».
   Фиолетовый настроен на (255,0,200):
   первоначальный (128,0,255) пользователь оценил как слишком синий.
   Первоначальный розовый (255,64,128) на этой ленте выглядел белым.
   Тёплый белый — приближение через RGB,
   отдельный белый канал и точная цветовая температура не заявляются.
2. **Питание.** «Чушпан, выключи подсветку», затем «Чушпан, включи подсветку».
   Проверяйте реальное гашение и возврат света. Чёрный RGB не используется как
   подмена выключения. При включении не отправляется скрытая команда цвета.
3. **Яркость.** На одном цвете последовательно задайте 100%, 25%, 50%, 0%, затем
   снова 50%. Пример: «Чушпан, установи яркость подсветки на пятьдесят процентов».
   «Сделай подсветку ярче/тусклее» меняет последний заданный уровень на 10 пунктов
   в пределах 0–100. После неизвестного результата записи яркости сначала нужен
   абсолютный уровень. Внешние изменения приложением телефона не отслеживаются.
4. **Статус и перезапуск.** «Чушпан, проверь состояние ленты». Перезапустите
   Чушпана и проверьте `led status`: подтверждения и журнал должны сохраниться.
   Ничего не отправляется при старте приложения или чтении статуса.
5. **Bluetooth и переподключение.** Выключите Bluetooth в macOS и запросите
   красный: должен прозвучать отказ, без сообщения об успехе. Включите Bluetooth
   и повторите просьбу: создаётся новое соединение. Отключите питание ленты —
   запрос завершится ошибкой или тайм-аутом. После возврата питания новая просьба
   снова подключается. Если разрыв произошёл во время записи, пакет не повторяется.
6. **Ночной сценарий.** Сначала выполните `uv run python -m backend night-check`.
   Когда готовы к существующему запуску видео и сна Mac, скажите «Чушпан, я спать»
   и подтвердите обычный код сценария. После прежних шагов BetterDisplay (10% и
   25%) и громкости Mac (30%) отправляется проверенное выключение LED; последним
   запускается прежний `Youtube sleep`. Ошибка LED или непроверенное выключение
   отмечаются как частичный результат, но не блокируют прежние действия.
   Повторное обращение не дублирует LED и Shortcut. Для проверки сбоя LED
   предпочтительны автотесты: живой ночной сценарий действительно может усыпить Mac.

При успехе Чушпан говорит «Команда … отправлена по Bluetooth», только после
завершения `await write_gatt_char`. Он не утверждает, что цвет физически изменился.
Даже запись без ошибки и сырое уведомление FFF4 не доказывают исполнение.
После ошибки или тайм-аута записи повторной отправки нет. До записи допускается
одна повторная попытка подключения. Соединение освобождается после каждой операции;
тайм-ауты подключения/записи/отключения ограничены.

## Автотесты

```sh
uv run pytest -q tests/test_led.py tests/test_night.py tests/test_latency.py tests/test_autostart.py
uv run pytest -q
uv run ruff check backend tests/test_led.py
```

Все тесты LED используют подставной транспорт и временную папку настроек.
Они не включают реальный Bluetooth, ленту, микрофон, BetterDisplay или Shortcut.
Проверяются протокол, русские фразы, запрет непроверенных режимов, визуальное
подтверждение, сохранение профиля, смена прошивки, тайм-ауты и отмена записи,
переподключение, отсутствие раннего ответа, обход LLM и прежние действия ночи.
