# Составные команды Чушпана

Разбор встроен в существующий `local_commands.route()` и `Conversation`.
Нового параллельного сервиса команд или LLM-запроса на каждый параметр нет.
Известные запросы обходят LLM целиком. Неразобранные параметры требуют уточнения;
сложные запросы вне этого маршрута сохраняют прежнюю систему tool calling,
проверки JSON Schema, доступных инструментов и исходного запроса.

## Архитектура

1. `command_text()` нормализует обращение и грамматические части. Исходный
   пользовательский текст сохраняется в `RequestContext` и истории.
2. Существующий `led.parse()` выделяет параметры ленты; локальный маршрутизатор
   и музыкальный парсер определяют поддерживаемые действия других интеграций.
   Объект команды проверяется отдельно от простого упоминания цвета в факте.
3. `ControlPlan` с дискриминированными Pydantic-моделями задаёт допустимые
   устройства и параметры. Неизвестные поля, устройства, инструменты,
   числовые значения вне диапазона и противоречия отклоняются.
4. `ControlSession.execute()` повторно сверяет план с полным исходным запросом
   и ограниченным контекстом перед любым действием.
5. Каждый шаг вызывает **существующий** `ToolRegistry.call()`. План выдаёт
   временное разрешение только на точные имя инструмента, аргументы и request ID.
   Авторизованная сессия, capabilities и Mac Agent по-прежнему обязательны.
   Опасные операции этим разрешением не охватываются.
6. Лента получает одну логическую операцию `led_control`: все её параметры
   выполняются внутри общей asyncio/межпроцессной блокировки устройства.
   Все режимы предварительно проверяются по наблюдениям конкретной прошивки.
7. После завершения формируются отдельные результаты шагов и короткий ответ.
   В историю записываются реальные вызовы и результаты инструментов, ошибки
   и исходная просьба. Диагностика использует прежние трассы маршрутизации,
   разрешений, BLE и инструментов, дополненные этапом проверки плана.

План для «Чушпан, сделай ленту светло-розовой и яркость на сто процентов»:

```json
{
  "intent": "compound_control",
  "actions": [{
    "intent": "device_control",
    "device": "led_strip",
    "parameters": {"power": true, "color": "#FF1020", "brightness": 100}
  }]
}
```

Это одна команда устройства и один вызов инструмента. Используется прежняя
**пользовательская калибровка**: светло-розовый `(255, 16, 32)`, розовый
`(255, 0, 32)`, тёплый белый `(255, 48, 32)`. Значение `#FFB6C9` из примера
структуры не заменяет эти экспериментально подобранные цвета.

## Поведение

- «Сделай ленту розовой на максимум», «Вруби светло-розовый на сто процентов»,
  «Ленту светло-розовую, яркость сотка», «Хочу нежно-розовую подсветку на полную»
  устанавливают соответствующий цвет и яркость 100%.
- «Включи LED-ленту на 100%, цвет светло-розовый» объединяет питание, цвет и
  яркость. Поддерживаются склонения, перестановка частей, «лед»/«лет»/LED,
  словесные числа от 0 до 100 и «наполовину».
- «Поставь розовый и сделай поярче» использует прежний относительный шаг +10
  процентных пунктов от последней успешно записанной яркости. Если она
  неизвестна, весь LED-пакет требует абсолютного значения до первой записи.
- «Сделай мне розовый свет, только не слишком яркий» ничего не отправляет,
  пока не задан `led.comfortable_brightness` или явный процент в запросе.
  На вопрос о проценте можно ответить «30», «тридцать процентов» или «на 30%»:
  ответ привязывается к исходной просьбе и тому же ограниченному сроку, без LLM.
  Например, пользователь может сам выбрать 35 в локальном `config.yaml`:
  `comfortable_brightness: 35`. По умолчанию значение `null`, числа не угадываются.
- «Убавь яркость экрана до 20%, включи тёплый свет и открой YouTube» использует
  существующие инструменты дисплея Mac, LED и открытия YouTube.
- «Выключи подсветку и поставь Mac на минимальную яркость» означает LED off и
  яркость дисплея 0%, без выключения или сна Mac.
- «Сделай ленту розовой, телевизор потише, а музыку включи» выполняет LED и
  музыкальную часть, отдельно сообщая, что управление громкостью телевизора
  не подключено. Громкость Mac вместо телевизора не меняется.

Операции разных устройств выполняются последовательно: некоторые интеграции
разделяют Safari и Mac Agent. Ошибка одного шага не отменяет следующие
независимые шаги. Зависимые записи внутри одной ленты прекращаются при ошибке.
Отмена пользователем останавливает оставшуюся часть всего плана.

BLE не объявляется атомарным. Сохраняются проверенные пакеты, `response=False`,
паузы контроллера и прежний способ подключения. Блокировка удерживается на
всю цепочку, хотя транспорт подключается для отдельных записей. Неудачная
запись автоматически не повторяется; повторное подключение допускается до
начала записи. Новая явная просьба может подключиться заново.

`device.json` сохраняет `last_transaction`: какие записи запрошены, отправлены,
неподтверждены или не начаты, включая частичный сбой и отмену. Успешный BLE write
обозначается `sent`; `physical_confirmed` остаётся `false`. Уведомления GATT
не выдаются за неподтверждённый протокол чтения состояния. Пример ответа:
«Команды подсветки записаны по Bluetooth: 3. включение, светло-розовый,
яркость 100%. Физическое выполнение не подтверждено».

Экран подтверждается перечитанным значением существующего Mac API. Музыка
сохраняет прежнюю проверку реального воспроизведения; одно намерение включить
не даёт права сказать «Играет». Открытие YouTube подтверждает только передачу
запроса macOS, без утверждения, что страница уже загрузилась.

## Контекст и повторные события

Контекст устройства живёт `tools.control_context_s` секунд (по умолчанию 60)
и привязан к авторизованной сессии и разговору. После «Сделай ленту розовой на
50%» фраза «Нет, лучше на 80» меняет **только яркость** той же ленты.
«Сделай светло-розовой» → «И яркость на максимум» работает аналогично.

Несколько разных устройств, неоднозначность, отмена, новый разговор или
истечение срока убирают однозначную привязку. После этого нужен вопрос
«Для какого устройства изменить яркость?». Контекст не предоставляет прав
опасным действиям и не отменяет ограничения голосовой активации.

Кэш последних 64 request ID не позволяет повторно выполнить уже начатый план,
включая частичный результат и отмену. На голосовом входе повтор того же
завершённого аудиосегмента отсеивается по его метке окончания. Одинаковая
фраза в новом аудиосегменте остаётся новой просьбой — текст не используется
как запрет намеренного повторения.

## Проверки

Добавлены 49 тестовых случаев в `tests/test_compound_intents.py`. Они используют
настоящие `Conversation`, `ToolRegistry`, Mac Agent, `LEDStrip`, функции Mac и
музыкальный контроллер. Подменены BLE-транспорт, нативный bridge, плеер и
открытие сайта. Личные `.env` и `data/` изолированы общей pytest-фикстурой.
На физическую ленту во время этих тестов команды не отправляются.

Проверяются все формулировки задания, один и несколько приборов, словесные
числа, контекст/TTL/сессии, конфликты, неизвестные режимы, частичное выполнение,
отмена, последовательность двух конкурентных BLE-транзакций, повторные STT и
request ID, сохранение памяти/предложений и защита опасных действий.
`NoModel` аварийно завершает тест при попытке обратиться к LLM.

Итог: 1544 Python-теста (49 новых случаев составных команд), 20 frontend-тестов,
Ruff, форматирование, TypeScript/Vite и `git diff --check` прошли.
Результаты полного прогона и статических проверок сохранены в
[`diagnostics/compound-intents/checks.json`](diagnostics/compound-intents/checks.json).
Примеры планов, их JSON Schema и замер парсера находятся в той же папке.
Замер из 200 прогретых разборов: медиана около 0,14 мс, p95 около 0,70 мс.
Это только локальный парсер, без STT, LLM, BLE и TTS; не время ответа живому
пользователю. Новая физическая проверка ленты в этой задаче не проводилась.

```sh
.venv/bin/pytest -q
.venv/bin/ruff check backend tests
.venv/bin/ruff format --check backend tests
npm --prefix frontend test
npm --prefix frontend run build
```

## Изменённые файлы этой задачи

- `backend/intents.py`: схема, компиляция плана, контекст, выполнение и защита от повторов.
- `backend/local_commands.py`, `backend/brain/conversation.py`: единый существующий маршрут
  локальных действий, история фактических результатов и сброс старого предложения.
- `backend/led.py`: грамматические параметры, предварительная проверка всей транзакции,
  общая блокировка и журнал отдельных записей.
- `backend/context.py`, `backend/tools/registry.py`: узкое разрешение конкретного шага.
- `backend/voice.py`, `backend/addressee.py`: безопасное продолжение и повторные STT.
- `backend/config.py`, `config.yaml`: TTL и необязательное предпочтение яркости.
- `tests/test_compound_intents.py`, `tests/test_smart_home.py`: новые сценарии и
  обновлённое ожидание явного power-on в составной команде.
- Этот документ, README и `docs/diagnostics/compound-intents/`.

Границы поддержки: дополнительных LED-устройств, эффектов, отдельного протокола
громкости TV и настоящей атомарности BLE здесь нет. Неподдерживаемая часть
не превращается в другой инструмент или произвольное значение.
