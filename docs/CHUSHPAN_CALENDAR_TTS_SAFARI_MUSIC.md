# Календарь, произношение, Safari Music и запоздалое «ой ну ща»

Работа продолжена с существующих изменённых файлов; прежние исправления аудио,
диалоговых сессий и адресата речи сохранены. Коммитов/push нет. `.env`, ключи,
пользовательская SQLite, голос и модель STT не редактировались. Настоящие системные
действия, воспроизведение музыки, запись микрофона и чтение личного календаря
при этой проверке не выполнялись.

## 1. Где терялись названия календаря

Реальный путь здесь — Google Calendar, синхронизированный с календарями macOS →
EventKit (`backend/personal.swift`) → `PersonalContext.read()` →
`calendar_sentences()` → поток утренней сводки → `speak_tokens()` →
`SileroSpeaker._synth()` → `speech_text()`/русская нормализация → `apply_tts()`.
Это не прямой запрос к Google Calendar API.

EventKit возвращает исходное `event.title`, форматтер сохраняет название, лишь
сворачивая пробелы. Найденная потеря содержания была в речевой подготовке:
неизвестные словарю иностранные слова заменялись на «название в тексте».
Поэтому добавления нескольких известных городов было недостаточно для занятий.

Ответы модели, инструменты, локальные реплики, утренний календарь, уведомления,
повтор ответа и подготовка waiting-кэша используют общий путь синтезатора.
Нормализация меняет только речевую копию. Исходные названия, UI и история сохраняются.
Словарь применяется к полным TTS-предложениям после сборки токенов, до их синтеза;
не выполняется посимвольная обработка входящего потока. Разделение предложений
не разрывает инициалы/аббревиатуры вида «Д. Т. П.».

Добавлены полные фонетические варианты девяти пользовательских примеров:
Diskreetne matemaatika, Programmeerimise algkursus, Andmebaasid, Tarkvaratehnika,
Sissejuhatus infotehnoloogiasse, IT süsteemide arendus, Jõhvi, Kohtla-Järve,
Tallinna Tehnikaülikool. Это тестовые названия, не результат чтения личного календаря.
Есть NFC-нормализация и обработка эстонских õ/ä/ö/ü, долгих гласных и сочетаний.
Неизвестное слово не заменяется заглушкой: используется приблизительная фонетическая
подготовка с явным признаком `estimated_foreign` в диагностике. Для английского
сначала используется существующий CMU-словарь настоящих фонем; произвольная латиница
не считается аббревиатурой только из-за верхнего регистра.

Русский Silero не воспроизводит все эстонские качества гласных и три степени
долготы. Приведённая подготовка приблизительна, без выдуманного перевода.
Нативное эстонское произношение не заявляется. Необычные названия стоит уточнять
в словаре, а качество образцов необходимо прослушать человеку.

## 2. Аббревиатуры и диагностика TTS

Расширяемые данные — `backend/audio/pronunciations.json`: разделы `names` и
`abbreviations`; у аббревиатур есть тип `letters`/`word` и готовое произношение.
Добавлены ДТП, ГИБДД, МЧС, МВД, API, HTML, CSS, SQL, USB, CPU и другие обозначения.
Обрабатываются точки/пробелы, API/CSS и USB-C. НАТО/МИД/вуз читаются словами,
бренды — целиком, обычный верхний регистр не вызывает универсальное чтение по буквам.
Пользовательские `tts.pronunciations` имеют приоритет. Словарь можно менять без
переписывания основного кода; после правки нужен перезапуск процесса.

URL, пути, секреты и код в исходном ответе не меняются. В речевой копии такие
фрагменты намеренно заменяются безопасным обозначением; диагностика считает их
отдельно, не выдавая это за пропущенные названия занятий. Логи содержат только
количество приблизительных слов, без самих названий.

Без микрофона и без воспроизведения:

```sh
.venv/bin/python -m backend tts-check --sample calendar
.venv/bin/python -m backend tts-check --sample abbreviations --synthesize
.venv/bin/python -m backend tts-check --sample mixed --synthesize
```

Для своего текста есть `--text-file`; содержимое скрыто по умолчанию.
`--show-text` — явное разрешение показать текст с маскированием защищённых литералов.
Синтез выполняется только при настроенном Silero и не подменяет другой движок.

Настоящим локальным `silero_v5_6_ru.pt`, голос `eugene`, созданы WAV без проигрывания:

- `docs/audio/tts-regression/calendar.wav` — 11,537 с, названия занятий.
- `docs/audio/tts-regression/abbreviations.wav` — 7,875 с, включая ДТП и API.
- `docs/audio/tts-regression/mixed.wav` — 6,950 с, русский/эстонский текст и сокращения.

Все WAV — mono PCM 24 кГц, имеют ненулевой сигнал; сведения и исходные тестовые
тексты сохранены в соседнем `manifest.json`. Непреобразованных латинских токенов
в нормализованных образцах нет. Это подтверждение синтеза, не независимая оценка
качества произношения. При загрузке существующего пакета Silero был его внутренний
`SyntaxWarning` об escape-последовательности; ошибок генерации аудио не было.

## 3. Что мешало YouTube Music

Прежний адаптер работал с отдельным Safari Web App и каталогом `ytmusicapi`.
Кроме того, незавершённая новая версия разделяла проверку Apple Events из Python
и исполнение через `osascript`: это разные отправители для разрешений macOS.
Теперь стандартный транспорт — обычная вкладка Safari и публичный DOM Music,
без вызова недокументированных API. Старый транспорт оставлен как отдельный режим.

Новый `music_safari.swift` в одном вызове процесса проверяет Carbon Automation
и исполняет `NSAppleScript`. По умолчанию проверка не запрашивает доступ, а отказ,
неопределённое состояние и недоступный Safari различаются. Swift и встроенный
Info.plist компилируются в кэш с хешем исходников; Python больше не использует
старую функцию ctypes или `osascript` для этого адаптера.

Проверка вне sandbox новым помощником получила `not_determined / -1744`.
В sandbox было `-600` — недоступность цели; это не интерпретируется как доказанный
отказ в разрешении. Safari установлен. Проверка вкладки/JavaScript/авторизации
остановлена до получения доступа; их состояние неизвестно. Это результат текущего
запуска `.venv/bin/python`, не доказательство разрешений отдельного приложения.

Реализованы повторное использование одной вкладки, отказ от выбора среди нескольких,
поиск и уточнение неоднозначных результатов, пауза/продолжение, предыдущий/следующий
трек, громкость, состояние плеера и основной сохранённый плейлист.
После перехода к песне адаптер ждёт нужное название в медиа, прежде чем продолжать
воспроизведение: прежний трек не возобновляется вслепую.
Результат запуска подтверждается только продвижением позиции готового плеера,
проверкой выбранных метаданных и отсутствием рекламы/выключенного звука в media.
Открытая страница сама по себе не считается успехом. После неопределённой ошибки
повторный автоматический запуск той же команды блокируется.

«Включи музыку» продолжает очередь; «Включи мой плейлист» использует существующее
назначение. Утренний сценарий сохраняет именно запуск назначенного плейлиста
после окончания речи, с предварительной проверкой тихой громкости. Если пустой
плеер не позволяет подтвердить её, сценарий сообщает ошибку, а не запускает громко.
Сценарий обычного YouTube для сна и команда `Youtube sleep` не менялись.

**Реальное воспроизведение ещё не подтверждено.** Проверки DOM и Apple Events
мокировались в автоматических тестах; защищённый браузер не обходился.
Полные ручные шаги и безопасные/живые команды: [youtube-music.md](youtube-music.md).

В работающем приложении доступны локальные команды «Чушпан, проверь YouTube Music»
и «Чушпан, разреши управление YouTube Music». Только вторая явно инициирует
системное подтверждение чтением числа окон Safari. Ни одна не запускает музыку.
Они полезнее проверки из другого Terminal для определения прав самого приложения.

## 4. Настоящая причина «Доброе утро → ой ну ща»

В `backend/brain/morning.py`, `MorningRoutine.stream()` была жёстко задана строка
`yield "Доброе утро. Ой, ну ща. "`. Она попадала в **основной** поток ответа и затем
в обычную очередь TTS. `allow_waiting()` уже исключал «Доброе утро», поэтому прежние
исправления таймера не могли убрать эту реплику. Это воспроизводится на настоящем
утреннем обработчике с подменёнными источниками и аудиоплеером, без Gemini.

Теперь утренний поток начинает с `Доброе утро.`. Все 18 waiting-фраз остались в
отдельном кэше. Простой социальный ввод, включая «Добрый вечер», и пустой ввод
не запускают таймер. Содержательный вопрос после приветствия сохраняет waiting.
«Спокойной ночи» остаётся прежним подтверждаемым локальным ночным намерением;
добавление waiting-защиты не меняет его выполнение или подтверждения.

Каждый речевой ответ имеет отдельного владельца. Отложенная waiting-задача перед
самим воспроизведением повторно проверяет владельца, готовность ответа и завершение
запроса. Таймер закрывается при готовности ответа, начале основного TTS и в finally.
Waiting отменяется и полностью дожидается остановки до основного TTS. Запоздалые
основные callbacks после завершения ответа игнорируются; завершённый аудиоплеер
также инвалидирует свои уведомления. Это дополняет прежние блокировки/stop-events,
а не заменяет их.

В INFO-логах есть `VOICE_EVENT`, монотонная временная метка `t` и request ID:
`REQUEST_RECEIVED`, `REQUEST_ROUTE`, `WAIT_TIMER_START`, `WAIT_TIMER_CANCEL`,
`WAIT_TIMER_SKIP`, `WAIT_AUDIO_START`, `WAIT_AUDIO_CANCEL`, `MAIN_AUDIO_START`,
`MAIN_AUDIO_END`, `REQUEST_COMPLETED`. Отрицательные ID используются только для
отдельного вызова речевого API вне основного голосового цикла; обычный цикл сохраняет
свои возрастающие ID. Содержимое запроса в этих диагностических событиях не пишется.

Реальных записей/логов проблемного голосового запуска не было: отдельный ложный
последующий запрос на устройстве не доказан. Тесты проверяют, что тишина и пустой
результат после приветствия не вызывают STT/новую очередь ответа; прежние acoustic,
echo, wake-word и addressee-защиты не ослаблялись.

## 5. Проверки и файлы

Финальный полный прогон: **1176 backend-тестов прошли**. Ruff — без ошибок.
Frontend — **10 тестов прошли**, `tsc --noEmit` и Vite build успешны.
Новый Swift-помощник прошёл typecheck и реально скомпилировался при безопасной
диагностике. `git diff --check` — без ошибок.

Проверено: все девять названий через календарный форматтер, поток и реальную границу
`apply_tts` с FakeSilero; сокращения, точки, регистр, Unicode и исходный UI;
отказы Automation/JS, авторизация, autoplay, повторное использование вкладки,
застывший/чужой/рекламный/беззвучный плеер, настоящие DOM-операции в Node VM;
локальное утро, быстрые/медленные ответы модели, поздние callbacks, повторные
приветствия, активная сессия, восстановление listening, приветствие после долгого
ответа, рабочий waiting на долгом запросе, тишина/пустой ввод и отмена таймера.
Проверки waiting наблюдают очередь настоящего синтезатора с подменённым `_play`,
а не только совпадение текста ответа. Системные действия тестами не выполняются.

Основные изменённые/добавленные участки текущей работы:

  `backend/brain/{morning,conversation}.py`.

## 6. Что проверить вручную

1. Перезапусти Чушпана обычным способом, чтобы загрузился изменённый Python-код.
   При ручном запуске: `.venv/bin/python -m backend voice --no-briefing`.
   Не запускай второй экземпляр поверх работающего.
2. Прослушай три WAV и оцени названия/ДТП/API. Затем проверь озвучивание названия
   существующего занятия; эти изменения не редактируют само событие.
3. Для проверки простых приветствий используй «Привет»/«Добрый вечер» в голосовом
   режиме и проверь отсутствие waiting после ответа; отдельно проверь длинный вопрос.
   Существующее «Доброе утро» также запускает настроенную утреннюю сводку/музыку,
   а «Спокойной ночи» — подтверждение ночного режима: не подтверждай системные
   действия ради тестирования ожидания. Утро без этих действий проверено моками.
4. Для Music сначала выполни безопасную диагностику в приложении, затем явно запроси
   разрешение и настрой Safari по инструкции. После этого отдельно, когда готова
   услышать музыку, запусти `music-check --live "Включи музыку" --json` или голосовую
   музыкальную команду. Подтверди нужный трек, слышимый звук и движение позиции.
