## Что изменилось по результатам проверки

В первой серии модель заявила об открытии IntelliJ без вызова инструмента.
Это реальный неуспех и источник новой защиты: до выполнения команды модельный
текст удерживается, при пропуске инструмента выполняется один повтор;
при повторном пропуске возвращается отказ. Теперь утверждение об исполнении
не проходит наружу в этих прямых сценариях без tool call. Регрессионный тест
проверяет и retry, и отказ, и отсутствие ложной фразы в истории.
Это ограниченная защита прямых команд, не доказательство истинности любой фразы LLM.

В итоговой серии открытие и заряд вызывают инструменты; запись факта ждёт код,
фактов после неё ноль. Java различает неинициализированную локальную переменную,
null-ссылку и default null поля; математика правильно различает −2² и (−2)².
Тяжёлая ссора получает конкретный серьёзный вопрос, без выдуманной смерти/утраты.
Feedback «короче» не записывает постоянного предпочтения: фактов по-прежнему ноль.

**Оставшиеся проблемы не устранены полностью:** в итоговом Java-ответе есть
«ты написал»; изначальную причину без исходника модель описывает слишком уверенно.
Бытовая усталость всё ещё получает непрошеные советы. Обычная беседа содержит
фиктивную человеческую обстановку; просьба поворчать — выдуманные свойства
компилятора и лишние рассуждения. Технические примеры исправлены по сравнению
с этапом 2, но универсальной проверки корректности суждений нет. Голосовые
настройки и модель не подменялись ради хорошего примера. Все ответы ниже сохранены
без редактирования, включая неудачные и промежуточные.

### Техническое объяснение

Пользовательница: «Почему student.getName() выбрасывает NullPointerException? Объясни на примере, я учусь Java.»

> Секунду. NullPointerException выбрасывается, потому что ты вызываешь метод на объекте, который не существует. В Java локальная переменная должна быть явно инициализирована — вот пример:
> 
> ```java
> Student student; // компиляция: ошибка "variable might not have been initialized"
> student.getName(); // не доживёшь до выполнения, если даже присвоишь null
> ```
>

> 
> Поля класса по умолчанию тоже `null` (если не указаны иначе), но локальные переменные — нет. Это ключевое различие. Чтобы исправить, либо инициализируй объект реальным экземпляром:
> 
> ```java
> Student student = new Student("Ivan");
> student.getName(); // работает
> ```
> 
> либо проверяй null перед вызовом:
> 
> ```java
> if (student != null) {
>     System.out.println(student.getName());
> }
> ```
> 
> Короче, NullPointerException — это не баг языка, а защита от обращения к несуществующему объекту.

### Java: локальная и поле

Пользовательница: «Чем отличается неинициализированная локальная переменная от поля типа Student в Java?»

> Секунду. В Java тут разница как между «я не знаю, кто ты» и «ты мне ничего не сказал».
> 
> **Локальная переменная**, например `Student student;` внутри метода, считается неинициализированной, если до её использования ты не написал `student = ...`. Компилятор это видит сразу — выдаст ошибку `variable might not have been initialized`, потому что он знает: ты не присвоил ей значение.
> 
> **Поле класса**, например `private Student student;` в теле класса, инициализируется автоматически null при создании экземпляра. Компилятор не требует явного присваивания — поле считается инициализированным по умолчанию.
> 
> Но вот загвоздка: если ты напишешь `student.getName()` на таком поле, будет NPE (NullPointerException) при выполнении, потому что `student` равен null. Компилятор не видит ошибки — он верит, что ты мог бы присвоить значение позже.
> 
> **Код для примера**:
> ```java
> class Student {
>     private String name;
>     
>     // getter без проверки на null
>     public String getName() {
>         return name;  // если student = null, тут NPE
>     }
> }
> 
> public class Main {
>     private Student student;  // поле, по умолчанию null
>     
>     public void test() {
>         System.out.println(student.getName());  // компилируется, но вылетит NPE
>     }
> }
> ```
> 
> **Итог**: локальная неинициализированная — ошибка компиляции. Поле с нулевым значением — компилируется, но выполнение может упасть на NPE.
