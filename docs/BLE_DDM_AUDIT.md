# ELK-BLEDDM: аудит и границы проверки

Дата: 6 ноября 2026 года. Диагностические экспорты и адреса устройств в исходники не включены.

## Что установлено

До исправления `backend/led.py` формировал единственный набор девятибайтовых
пакетов для всех лент, использовал настройки FFF0/FFF3 основной ELK-BLEDOB и
только `response=False`. В `Devices.strip()` менялись адрес, имя и прошивка,
но сериализатор оставался прежним. Для устройства без BLE-имени наследовалось
даже имя основной ленты. `inspect()` рассматривал только FFF0 и отвергал
остальной GATT, поэтому не позволял диагностировать иной контроллер.

`ba705ed` расширил поиск имён и передачу результатов в интерфейс. Он не добавил
отдельного протокола ELK-BLEDDM. Обнаружение, соединение и завершившаяся запись
байтов не доказывают применение команды контроллером.

В первичной реализации
[elkbledom/models.json](https://github.com/dave-code-ruiz/elkbledom/blob/main/custom_components/elkbledom/models.json)
ELK-BLEDDM имеет собственные шаблоны:

- включение: `7E 04 04 F0 00 01 FF 00 EF`;
- выключение: `7E 04 04 00 00 00 FF 00 EF`;
- RGB: `7E 00 05 03 RR GG BB 00 EF`;
- яркость: `7E 04 01 LL FF 00 FF 00 EF`, LL — процент 0–100.

У существующего драйвера RGB начинается `7E 07 05 03` и заканчивается `10 EF`;
включение использует `01` вместо `F0`, а яркость содержит другие служебные байты.
Исходный пакет выключения совпадает. Это конкретное различие протоколов,
а не вывод о совместимости по похожему названию.

Существующий драйвер сохранён побайтно по
[CommandUtils.kt](https://github.com/user154lt/ELK-BLEDOM-Command-Util/blob/master/CommandUtils.kt).
У upstream есть и другие варианты GATT; они автоматически не перебираются.

## Реальная диагностика без управления

С отдельного разрешения пользователя выполнены подключение, перечисление всех
сервисов, чтения и подписка на уведомления выбранной физической ELK-BLEDDM.

Обнаружен один сервис `0000fff0-0000-1000-8000-00805f9b34fb`:

- `0000fff3-0000-1000-8000-00805f9b34fb`: read, write, write-without-response;
  чтение 32 байт успешно; доступны оба режима записи.
- `0000fff4-0000-1000-8000-00805f9b34fb`: read, notify;
  чтение 32 байт успешно; получено одно уведомление длиной 3 байта.

Подписка завершена, соединение закрыто, ошибок в успешном отчёте нет.
Управляющих пакетов отправлено **0**. Содержимое чтений/уведомлений скрыто.
Первый запуск внутри sandbox не имел доступа к Bluetooth-адаптеру; разрешённый
повтор вне sandbox завершился успешно.

Отсутствие FFF3 и неподдерживаемый режим `without-response` для этого устройства
исключены. Применение неподходящих пакетов — основная обоснованная гипотеза
отказа. **Причина отсутствия реакции не подтверждена окончательно:** новые
пакеты не отправлялись и видимый результат не наблюдался. Уведомление не является ACK.

## Изменения архитектуры

- `backend/ble_profiles.py`: отдельные legacy и DDM-кандидат, строгие JSON-профили,
  сериализация, явные service/write UUID и режимы response/without-response/auto.
  Неоднозначные характеристики и несоответствующие свойства блокируют запись.
- `backend/led.py`: все GATT-сервисы, ограниченные по времени чтения и уведомления,
  журнал этапов и ошибок, обезличенный JSON-отчёт с правами 0600 в личном data/.
  В экспорт не попадают имя/адрес, сырые значения и сообщения исключений.
- Подтверждения привязаны к устройству, прошивке, драйверу и структуре GATT.
  Смена профиля сбрасывает допуски, незавершённую проверку и опорную яркость.
  Старые допуски DDM от legacy-сериализатора не разрешают новые пакеты.
- `backend/devices/service.py`: профили и диагностика выбранной ленты,
  сохранение прежних проверок доступа/локации и отдельных журналов устройств.
- `backend/led_cli.py`: `--device` для выбранного реестрового устройства,
  `profile` для явного выбора/импорта, предварительный просмотр пакета при `probe`.
- `frontend/src/devices.ts`: существующее фиолетовое оформление, статус драйвера,
  GATT и подтверждений функций, диагностика/скачивание отчёта, импорт профиля.
  Ответы проверки привязаны к конкретному устройству при смене выбранной карточки.

DDM выбирается только как **кандидат**. Обычные голосовые команды, LLM и сценарии
не включают экспериментальный режим. Перед тестом DDM/импортированного профиля
нужна успешная проверка его GATT. Один выбранный тест требует отдельного согласия;
допуск функции появляется только после визуального подтверждения человеком.
В последующем исправлении [RGB_EDITOR.md](RGB_EDITOR.md) общий RGB-допуск
разрешается после одного явно подтверждённого теста цвета. Проверка яркости
по-прежнему остаётся отдельной.

Переподключение повторяется один раз только до начала записи. После начала
записи нет автоматического повтора, переключения UUID или режима записи.
Следующая явная просьба создаёт новое соединение. Последние отправленные значения
сохраняются отдельно от фактического состояния; при запуске/переподключении
команды не воспроизводятся. Окончание BLE-записи остаётся «отправлено,
физическое выполнение не подтверждено», включая запись с ATT-ответом.

Голосовая маршрутизация остаётся в `backend/devices/center.py`, `backend/intents.py`,
`backend/voice.py` и реестре инструментов: имя/синоним/место определяют конкретную
ленту; неоднозначная просьба при нескольких лентах требует уточнения. Запись
всегда проходит через выбранный драйвер и локальный контроль доступа.

## Применение

В карточке выбранной ленты: «Диагностика» → проверить GATT и выбранный драйвер →
«Проверить управление» → выбрать ровно одну функцию → подтвердить видимый результат.
Смена профиля и диагностика сами управляющих команд не посылают.

CLI, где `DEVICE_ID` — локальный id из раздела устройств, а не BLE-адрес:

```sh
.venv/bin/python -m backend led inspect --device DEVICE_ID
.venv/bin/python -m backend led profile elk-bleddm-candidate --device DEVICE_ID
.venv/bin/python -m backend led inspect --device DEVICE_ID
.venv/bin/python -m backend led probe "включи ленту" --device DEVICE_ID
```

Для профиля с подтверждённым захватом вместо имени драйвера передаётся путь JSON.
Импорт до 32 КБ поддерживает только power/RGB/brightness: байты 0–255 и поля
`r`, `g`, `b`, `level`. Выполняемый код, startup/login/query-команды и неизвестные
действия запрещены. Обязательны `id`, `name`, `source`, полные `service` и
`write_characteristic`, `commands`; `write_mode` задаётся явно или остаётся
`without-response`. Пример структуры можно получить из `DDM_PROFILE.model_dump()`;
она является кандидатом, а не свидетельством совместимости устройства.

Для реестра установленного приложения CLI запускается с `CHUSHPAN_DESKTOP=1`.
Само приложение в рамках этой задачи не переустанавливалось.

## Проверки и оставшаяся работа

Автоматические тесты используют исключительно mock BLE. Они проверяют различные
GATT, оба режима записи, неизвестные модели, импорт, защиту от утечки значений,
ошибки/отмену/тайм-ауты, смену драйвера/GATT, сохранение состояния, отсутствие
автоповтора и независимые команды двум лентам через голосовой маршрут.
UI-тесты проверяют отсутствие управляющих действий при диагностике и правильную
привязку ответа теста при смене карточки.

На физической ленте в этой задаче проверены **только соединение/GATT/read/notify**.
Включение, выключение, RGB и яркость DDM требуют отдельного разрешения на запись
и наблюдения результата. Тёплый белый остаётся прежней RGB-имитацией; наличие
отдельных тёплого/холодного белых каналов на этой ленте не установлено, команды
для них не добавлены. Реальное управление ELK-BLEDDM и отсутствие аппаратных
регрессий ELK-BLEDOB пока не подтверждены.

Проверки последней версии BLE-изменений: **178 Python-тестов** (LED, discovery,
профили, устройства, голосовые маршруты и runtime), **158 frontend-тестов**,
`npm run build`, Ruff check и Ruff format check прошли. Широкий прогон вне
sandbox: **2530 passed**; из него исключён отдельно разрабатываемый
`tests/test_ui_qa_backend.py`, появившийся параллельно и не относящийся к BLE.
Его первоначальный запуск имел ошибку тестовой авторизации. В sandbox также
не проходил тест UNIX-сокета singleton; повтор вне sandbox прошёл.

Полный список файлов этого изменения:
