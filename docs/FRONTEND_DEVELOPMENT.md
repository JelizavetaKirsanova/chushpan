# Frontend-dev: Vite HMR в нативном окне Чушпана

## Устройство режима

Обычная оболочка создаёт WKWebView через pywebview, запускает свой Python worker и получает его loopback URL из приватного endpoint-файла. Worker обслуживает `/ws`, `/_desktop`, `/cinema/...` и готовый `frontend/dist`. Авторизованные служебные команды оболочки используют отдельный `X-Chushpan-Token`; интерфейс получает события через существующий WebSocket с проверкой Origin.

При явном `--frontend-dev` этот worker остаётся настоящим. После публикации его endpoint оболочка запускает принадлежащий ей Node-процесс `frontend/scripts/desktop-dev.mjs`, который поднимает Vite API на `127.0.0.1:5173`. WKWebView загружает Vite; `/ws`, `/_desktop` и `/cinema` проксируются на адрес именно этого worker. Адрес авторизованного управления Python не заменяется адресом Vite. Проверка готовности dev-интерфейса использует исходный HTML, `/@vite/client` и `/src/main.ts`; `frontend/dist` для dev-запуска не требуется.

HMR использует отдельный путь `/__vite_hmr`, поэтому не пересекается с WebSocket приложения `/ws`. Изображения и другие ресурсы `frontend/public` доступны через Vite по прежним URL. URL Vite не добавляется в production-фронтенд. Изменения Python требуют перезапуска dev-конфигурации.

## PyCharm

Откройте существующий `my-jarvis` через File → Open, используйте интерпретатор `.venv/bin/python`. В проекте уже есть две общие `.run/*.run.xml` конфигурации без абсолютных путей компьютера:

- **Chushpan Frontend Dev**: модуль `backend.desktop`, аргументы `--frontend-dev --no-auto-listen`, рабочая папка `$PROJECT_DIR$`, отдельный профиль `$PROJECT_DIR$/private/frontend-dev.noindex/profile`.
- **Chushpan Production Build**: модуль `scripts.build_macos`, штатная сборка и проверка приложения; установщик не запускается.

Одна Python-конфигурация управляет одновременно работающими Vite и backend. Отдельный Compound с независимым npm-процессом не требуется: он затруднил бы привязку к случайному порту worker и владение процессами при Stop. Не запускайте параллельно `npm run dev` на том же порту.

Если конфигурации не появились, выполните File → Reload All from Disk и откройте список Run → Edit Configurations. Проверьте, что открыта корневая папка проекта и выбран его Python SDK. Если отсутствуют frontend-зависимости, один раз выполните `npm --prefix frontend ci`. Node ищется в PATH IDE и стандартных каталогах Homebrew. Нужна версия Node, совместимая с установленным Vite.

Нажмите Run → **Chushpan Frontend Dev**, дождитесь окна и готового backend. Откройте медиатеку, измените нужное правило в `frontend/src/cinema.css` и сохраните Cmd+S. CSS обновляется в текущем документе. TypeScript обновляется через граф модулей Vite: у модулей без HMR-обработчика выполняется автоматическая перезагрузка страницы. Несохранённые формы и временное состояние страницы могут потеряться при такой перезагрузке; сохранённые настройки не сбрасываются.

Изменения в Safari Styles временные: для постоянной правки перенесите значение в исходный CSS. Если изменение CSS не видно, в Computed проверьте, не перекрывается ли правило более специфичным селектором или другой темой.

## Профиль и безопасность

CLI без IDE:

```sh
.venv/bin/python -m backend.desktop --frontend-dev --no-auto-listen
```

По умолчанию CLI и конфигурация PyCharm используют один отдельный постоянный dev-профиль в `private/frontend-dev.noindex/profile`. Это пустой профиль с реальным backend, а не демонстрационные данные. Микрофон не запускается автоматически. Записи установленного приложения не импортируются и не изменяются. Для другого отдельного профиля можно явно задать абсолютный `CHUSHPAN_APP_DATA`; в общих настройках проекта используйте макрос `$PROJECT_DIR$`.

Vite слушает строго IPv4 loopback с `strictPort`: при занятом 5173 не выбирает случайный порт и не подключается к чужому серверу. Оболочка ждёт отдельный сигнал по pipe от своего Node-процесса после успешного `listen`, прежде чем загружать страницу. Backend также остаётся на `127.0.0.1`. Прокси сохраняет Origin, Host и существующую авторизацию. Неверный токен и посторонний WebSocket Origin по-прежнему отклоняются backend. Vite не читает `.env`, не получает служебные токены или переменные `VITE_*` из процесса приложения; файловый доступ Vite ограничен `frontend/`. Личные настройки не добавляются в frontend.

В packaged `.app` флаг `--frontend-dev` отклоняется до запуска оболочки. Обычный запуск из исходников также не запускает Node и не подключается к Vite. Режим Safari Inspector из `7a0a9dc` сохраняется: frontend-dev включает его автоматически, production допускает только отдельный явный `--developer-mode`.

## Инспектор, завершение, сборка

В Safari включите функции веб-разработчика и откройте Разработка → Inspect Apps and Devices → текущий Mac → Python → 127.0.0.1. Если запущено несколько исходных экземпляров, проверьте `location.origin` в Console: нужный — `http://127.0.0.1:5173`. Elements показывает классы, правила из исходных CSS-файлов, Computed и box model; Sources содержит исходные TypeScript-модули. Подробнее: [Safari Web Inspector](SAFARI_WEB_INSPECTOR.md).

Останавливайте **Chushpan Frontend Dev** кнопкой Stop в PyCharm либо завершайте этот экземпляр через меню Чушпана. Оболочка закрывает управляющий stdin Node и ждёт завершения Vite, затем останавливает свой worker. EOF stdin также закрывает Vite, если IDE принудительно убила родительский Python. Worker следит за своим родителем. Чужие Python/Vite-процессы не завершаются. При проблеме запуска смотрите `private/frontend-dev.noindex/profile/data/logs/{desktop,application}.log`, затем используйте «Переподключить интерфейс» или перезапустите конфигурацию.

После разработки остановите dev-режим. Для production-фронтенда:

```sh
npm --prefix frontend run typecheck
npm --prefix frontend test
npm --prefix frontend run build
```

Для полноценной macOS-сборки нажмите **Chushpan Production Build** или выполните `.venv/bin/python -m scripts.build_macos`. Штатный сборщик устанавливает frontend-зависимости из lock-файла, собирает `frontend/dist`, native-компоненты и `.app`, подписывает и проверяет пакет в каталоге сборок. Production-приложение не устанавливается и не перезапускается. Пользовательскую установку выполняют отдельно штатным установщиком, когда она понадобится.
