# Accessibility установленного Чушпана 0.3.15 (28)

Причина отказа в 0.3.14 установлена по системному журналу tccd, без чтения базы TCC. Swift-процесс `local.chushpan.ytmusic-ax` обращается к AX API, но TCC определяет ответственным приложение `ee.chushpan.desktop`. Для Accessibility журнал сообщает `Failed to match existing code requirement`: сохранённое требование содержало старый CDHash `39e58cb9219d27290935adce3f50e612856eb507`, установленное приложение — `a7ff07be9d87253e610bcbdb7f2bb29fec1d8c60`.

Цепочка: Launch Services → `/Applications/Чушпан.app/Contents/MacOS/Chushpan` → тот же бинарник с `--desktop-worker` → `/Applications/Чушпан.app/Contents/Frameworks/native/ytmusic_ax`. Путь `Contents/Resources/native/ytmusic_ax` ссылается на этот же файл. В установленной цепочке нет внешнего Python, shell или компиляции Swift. Отдельная разрешённая запись помощника не устраняет несовпадение требования основного приложения. Запуск из Codex проверяет другую ответственную цепочку и поэтому не является проверкой установленного приложения.

Оба исполняемых файла имели корректную ad hoc подпись; designated requirement основного приложения фиксировал CDHash. При обновлении подпись менялась. На этом Mac `security find-identity -v -p codesigning` не нашёл доступных идентичностей для подписи. App Sandbox и Hardened Runtime не включены; отсутствие специального AX entitlement не является причиной отказа. Исполнитель AX использует ApplicationServices, Apple Events используются отдельно для Safari и открытия страницы. В новую подпись основного приложения включён существующий entitlement Apple Events. Приватные entitlements не добавлялись.

Исправления: свежий процесс настоящего AX-исполнителя возвращает PID, PPID, фактический путь, bundle ID, enclosing app, обе проверки доверия и код чтения AXWindows Safari без содержимого окон. Центр разрешений показывает цепочку, подписи помощника и приложения, инструкцию перезапуска и кнопку «Проверить разрешения». Эта кнопка выполняет новый вызов API. Отказ API теперь явно показан как отсутствие доступа.

Действие «Обновить разрешение этой копии» требует подтверждения в интерфейсе, доступно только в подписанном каноническом установленном приложении и только при отсутствии доступа. Оно вызывает штатный `tccutil reset Accessibility ee.chushpan.desktop`, затем стандартный запрос AX и настройки macOS. Пользователь снова включает Чушпан и полностью перезапускает приложение. Чужие записи и другие категории разрешений не сбрасываются. База TCC не читается и не изменяется напрямую.

Установщик сохраняет старое и новое designated requirement и предупреждает при смене идентичности. Для сборок предусмотрен `CHUSHPAN_CODESIGN_IDENTITY` с настоящим доступным сертификатом: одна идентичность передаётся PyInstaller, нативным компонентам и основному приложению. Без сертификата используется явно обозначенная ad hoc подпись; сохранение разрешения между такими обновлениями не обещается. Ни сертификат, ни новая доверенная корневая запись автоматически не создаются. О связи разрешений и стабильного требования подписи: [Apple, TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements).

Установлена `/Applications/Чушпан.app` 0.3.15 (28), чистая сборка коммита `2126a16c1863bed021401e40dad5ac0005e1a835`. Глубокая строгая проверка подписи и установленная проверка импортов пройдены. Новый CDHash основного приложения — `5a78a8507abfae645bba5481cb8e8018e24a752c`. Предыдущие процессы завершены перед установкой; приложение запущено через Launch Services из /Applications с отключённым автоматическим прослушиванием.

Свежая проверка в установленном worker PID 88241 запустила AX-исполнитель PID 88360, PPID 88241 по пути Frameworks/native/ytmusic_ax. Обе проверки доверия вернули false. Настоящий вызов AXWindows к работающему Safari вернул AXError -25211 (apiDisabled). В журнале tccd снова подтверждено несовпадение старого требования 39e58c… и текущего 5a78a8… для `ee.chushpan.desktop`. Это реальный отказ AX API, а не только неоднозначный preflight. Отчёт в интерфейсе теперь показывает denied, точную идентичность и эти результаты.

90 целевых тестов Python, 195 тестов интерфейса, Ruff, проверка форматирования, TypeScript и сборка интерфейса пройдены. Контрольные хеши шести личных таблиц (произведения, серии, медиатека, история, ссылки, метаданные) до и после установки совпали. Поиск и менеджер временных вкладок не изменены.

После разблокировки 8 ноября 2026 года восстановление выполнено через интерфейс установленной 0.3.15: Настройки → Доступ и безопасность → «Обновить разрешение этой копии» → подтверждение → включение «Чушпан» в системном списке Accessibility. Сброшена только устаревшая запись Accessibility `ee.chushpan.desktop`, стандартный запрос зарегистрировал текущую копию. Отдельное разрешение помощника не потребовалось. Обе проверки доверия сразу вернули true, а чтение AXWindows Safari — AXError 0. Кнопка «Проверить разрешения» проверена в интерфейсе; статус стал «Разрешено».

Затем Чушпан полностью завершён через ⌘Q. Через ps подтверждено отсутствие оставшихся процессов пакета, приложение вновь запущено из /Applications. Доступ сохранился: свежий помощник PID 91692, родитель — установленный worker PID 91647, обе проверки true, AXError 0. Во время проверок ниже сборка и подпись больше не менялись.

Реальные запуски выполнены в личной медиатеке установленного приложения, без подмены адаптера или запуска плеера из среды разработки:

- S01E01: постер «Последнее королевство» → обучение на точной контрольной странице Kinogo → «Плеер 1», LostFilm → «Проверить и сохранить». Выбраны первый сезон и первая серия. Подтверждён таймер 0:00 → 0:01 при длительности 59:02 (3542 с), сценарий сохранён. Диагностическая вкладка автоматически закрылась.
- S01E01, обычный просмотр: из карточки нажата «Найти и смотреть». Чушпан использовал сохранённый сценарий, выбрал эпизод и включил видео; установленный backend сообщил PLAYING и подтвердил движение времени. В Safari наблюдался таймер 0:05 → 0:20 из 59:02. После «Сохранить и закрыть» в базе осталось 0:30.
- S01E02: существующей кнопкой карточки загружен список серий сезона, в Чушпане выбрана «Серия 2 · Вторая серия», нажата «Найти и смотреть». Сохранённый сценарий автоматически выбрал в Safari первый сезон, вторую серию и LostFilm. Подтверждён PLAYING, видимый таймер 0:12 → 0:38 из 58:42 (3522 с). После «Сохранить и закрыть» в базе осталось 0:43. Повторное обучение для второй серии не потребовалось.

Подтверждалось движение таймера полного эпизода в выбранном iframe, соответствие сезона/серии/озвучки и полного хронометража. Открытие страницы само по себе успехом не считалось. Прямое чтение HTMLMediaElement.currentTime чужого iframe не использовалось; в этом Safari-сценарии время подтверждено доступным таймером самого плеера. Полные 59 минут каждой серии не просматривались: проверены запуск и устойчивый рост времени.

Перед просмотром зафиксированы 2 пользовательских окна и 15 вкладок Safari. После обучения, после S01E01, после S01E02 и после последующего перезапуска список идентификаторов окон, URL и порядок вкладок точно совпал с исходным. Во время S01E02 была ровно одна помеченная видеовкладка Чушпана, исходные пользовательские окна и вкладки оставались неизменными. После закрытия не осталось ни одной помеченной служебной вкладки или дополнительного окна.

После второго полного завершения приложения база открыта только для чтения: S01E01 — 30/3542 с, S01E02 — 43/3522 с. Сохранены точный URL, «Плеер 1», LostFilm, сезон 1, серия 2 и ссылки для обеих серий. После нового запуска Accessibility снова granted; свежий помощник PID 92087, родитель — установленный worker PID 92047, обе проверки true, AXError 0. В интерфейсе после перезапуска медиатека также показывает «Смотрю · Сезон 1 · Серия 2» и «0:43 из 58:42», доступна кнопка продолжения. Старый отказ Accessibility устранён, обе серии реально запущены именно установленным Чушпаном.

Остающееся ограничение обновлений: эта локальная сборка подписана ad hoc, поэтому следующее изменение CDHash может снова потребовать штатного обновления разрешения. Поддержка постоянного сертификата добавлена, но сертификат на этом Mac отсутствует. Успех относится к проверенной странице Kinogo и плееру api.nextembed.ws; совместимость всех сайтов этим тестом не устанавливается. Микрофон не включался. Использованы только штатные средства восстановления разрешения; прямой доступ к базе TCC, изменение SIP и обход DRM, CAPTCHA или авторизации не применялись.
