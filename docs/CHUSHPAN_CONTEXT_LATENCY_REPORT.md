# Контекст диалога и задержки — 1 ноября 2026

Работа выполнена поверх существующих файлов, без отката прежних исправлений.
`.env`, ключи, русский голос Silero, Whisper large-v3-turbo, факты памяти,
назначение музыкальных плейлистов и ночной Shortcut `Youtube sleep` не менялись.
Commit/push не выполнялись. Настоящая музыка, видео, яркость, громкость и микрофон
во время проверки не запускались.

## Причины потери контекста

В существующей архитектуре один `Conversation` уже обслуживал несколько голосовых
команд. Новая SQLite conversation создавалась при обычном перезапуске без `--resume`,
а идентификатор устройства/сессии по умолчанию был новым UUID. Кроме того:

- Gemini получал только последние 8 сообщений, включая tool call/result.
- Результаты инструментов длиннее 300 символов заменялись заглушкой **до записи
  в SQLite**, поэтому исходные данные затем нельзя было восстановить из истории.
- После вызова инструмента предыдущая история удалялась из запроса при подготовке
  следующего ответа. Это историческая защита от копирования текста локальной моделью,
  но она применялась также к Gemini.
- У ассистента не было сохраняемого ожидающего предложения «посмотреть плейлисты».
  Согласие «давай, посмотри» попадало в модель без однозначной привязки к действию;
  локальная проверка адресата также не знала о таком предложении.

## Что изменено

Используется та же SQLite. Добавлена небольшая таблица `dialogue_sessions`, которая
связывает **доверенный, выданный backend session_id** с conversation_id. Локальный
desktop session_id сохраняется в существующих `preferences`. Mac voice и terminal
chat возобновляют эту сессию при перезапуске; первое обновление привязывает уже
имеющийся последний разговор. `/new` явно начинает новый разговор и обновляет
привязку. Другой экземпляр `Conversation` этой сессии подхватывает её изменение.
История не сбрасывается при окончании окна прослушивания wake-word.

В одном backend/MemoryStore запросы общей conversation сериализуются. Отдельные
SQLite-соединения также не могут дважды забрать одно ожидающее предложение:
проверка/потребление выполняется транзакционно. Предложения не являются очередью
системных действий и сами по себе ничего не запускают.

Новые вызовы инструментов и полные результаты, очищенные существующим фильтром
секретов, записываются в `messages`. Подписи мыслей Gemini и transient native parts
не сохраняются. Ранее уже сокращённые результаты автоматически не восстанавливаются.
В облако идёт до 24 последних сообщений текущей conversation, бюджет истории —
24 000 символов. Только исходящая копия длинных tool results сокращается; для
плейлистов сохраняются проверенные ID/названия первых 20 элементов и явный признак
неполного исторического списка. При переполнении удаляются старые законченные группы,
а не произвольные части tool call/result. SQLite остаётся полной.

Локальный контекст также учитывает настроенный `num_ctx` и резерв для ответа.
Для облака не используется меньший лимит окна Ollama: метаданные официального SDK
показали input_token_limit=1 048 576 для обеих настроенных облачных моделей.
Все сообщения других conversation и все факты SQLite автоматически в историю
добавляться не стали. Существующие правила персональной памяти сохранены.

Gemini теперь сохраняет историю при продолжении после инструментального вызова.
Прежняя защита Ollama от копирования ответа оставлена. Облачный фоновый warm-up
не планируется: удалённый `prime()` и так не генерирует ответ, а лишние фоновые
чтения истории и подготовка промпта здесь не нужны.

Обычная история уже доступна отдельно от логов в разделе «История» интерфейса:
он показывает пользовательские сообщения и ответы. Полные инструментальные
события сохраняются отдельно как tool/assistant tool_calls в той же SQLite.

## Предложения, согласия и плейлисты

Для конкретного сценария просмотра плейлистов сохраняется одно узкое предложение
`music_playlist(action=list)` с TTL 10 минут, привязанное к conversation.
Предложение возникает из явной положительной реплики ассистента «Могу посмотреть…»;
отрицание, цитата и альтернативы через «или/либо» не принимаются за согласованное
действие. Новая несвязанная реплика/объявление снимает старое предложение.

Согласия «да», «давай», «давай, посмотри», «сделай», «попробуй ещё раз» выполняют
именно предложенное **чтение списка**, без Gemini и без запуска музыки. Результат
форматируется из реальных полей `playlists[].title`; пустой/неполный/ошибочный список
не выдаётся за полный успешный результат. После ошибки чтения можно явно повторить
его через новое предложение. После неопределённого результата запуска музыки
автоматический повтор воспроизведения по короткому согласию не производится.

Короткое «открой» без конкретного объекта вызывает уточнение, а не превращается
в запуск случайного плейлиста. Другие неподдерживаемые/неоднозначные согласия также
не становятся системными действиями. Опасные действия по-прежнему используют
существующий механизм подтверждений; он не воссоздаётся из текста старой истории.

Контекстное голосовое согласие принимается только при активной голосовой сессии,
подтверждённой речи, уверенном STT и отсутствии эха. Строгий режим обязательного
обращения по имени сохраняется. Узкое server-side разрешение относится только
к конкретному READ-вызову и его аргументам. Оно не отменяет аутентификацию,
capabilities, Mac Agent, Automation или системные подтверждения.

Добавлены быстрые точные маршруты «Открой мой любимый плейлист», «Открой мой
плейлист», «Покажи мои плейлисты», «Посмотри доступные плейлисты». Открытие страницы
отделено от воспроизведения. Safari должен вернуть фактический URL нужной вкладки;
несовпадение не записывается как успешное открытие. Предпочтение плейлиста не
сохраняется при простом просмотре списка; прежний assign требует надёжно найденного
плейлиста и явного действия пользователя.

### Что выяснено о Favourite Songs

Read-only проверка настроек/SQLite показала: реальное сохранённое название —
**Favourite Songs**, ID имеется. В config также задано Favourite Songs, без ID.
Переименовывать его в `Favorites Songs` или назначать случайный плейлист оснований нет.
Новый точный маршрут использует существующее сохранённое назначение.

В текущем диагностическом запуске Python нативный помощник вернул
`automation=not_determined`, `osstatus=-1744`. Проверка остановилась **до** чтения
вкладки/авторизации/плейлиста. Это конкретная обнаруженная преграда этого запуска,
но не доказательство идентичных разрешений уже работающего приложения «Чушпан».
Существование сохранённого ID в сегодняшней библиотеке и реальное открытие/звук
пока не подтверждены. Музыка автоматически для проверки не включалась.

Проверка в самом приложении: «Чушпан, проверь YouTube Music».
Явный запрос системного диалога: «Чушпан, разреши управление YouTube Music».
Точные настройки Automation/JavaScript/autoplay остаются в [youtube-music.md](youtube-music.md).

## Mac и iPhone: граница подтверждённого

Backend поддерживает общую conversation для разных аутентифицированных DeviceContext,
если доверенная серверная сторона выдаёт им один session_id. Это проверено тестами
для Mac/iPhone, включая сохранение источника сообщений, перезапуск и `/new`.
Другая сессия и неаутентифицированный клиент не наследуют ожидающее предложение.
Описательный device_id не выдаёт права управления Mac.

В проекте не найден готовый входящий voice/chat API для iPhone: существующий HUD
WebSocket обслуживает интерфейс, а не является аутентифицированным телефонным
голосовым шлюзом. Новый открытый сетевой шлюз не создавался. Поэтому физический
переход Mac → настоящий iPhone не объявляется проверенным; телефонный вход должен
передавать именно проверенную backend-сессию, а не произвольный ID из клиентского JSON.

## Профилирование и скорость

Существующий `Profile` уже измеряет STT, подготовку контекста, каждый LLM attempt,
tool execution, TTS generation и начало звука. Он используется голосовым циклом
и интерфейсом диагностики. Сохранены request ID, отмена ожидания и потоковое
озвучивание по предложениям; промежуточные фразы не добавляются в историю ответа.

Реальное узкое место в этой проверке — **ожидание облачной попытки и затем fallback**.
До изменений первая модель отвечала 504/таймаутом спустя 14,21–15,01 с. Почти весь
общий бюджет был потрачен, затем отвечала локальная Ollama `qwen3:8b`.

Теперь отдельная облачная попытка ждёт первого результата до
`gemini.attempt_timeout_s=6`, сохраняя общий облачный бюджет `timeout_s=15`.
Резервной облачной модели остаётся время ответить. После первого полезного чанка
живой текстовый поток получает остаток исходного общего бюджета и не обрывается
просто из-за окончания первых 6 секунд. После частичного текста ответы не
перезапускаются другой моделью. Инструментальные ответы остаются буферизованными
до полной валидации; частичные tool calls не выполняются.

Для обычных объяснений вроде «Что такое…», «Объясни…», «Расскажи о…» добавлен
существующий текстовый streaming-маршрут без tool schemas. Он не применяется
к явным запросам действий. Модели, thinking level и язык не менялись.
Короткое согласие на просмотр плейлистов больше не требует ни интерпретации
большой моделью, ни второго модельного вызова для озвучивания результата.

Whisper, Silero и SDK-клиент в голосовом режиме создаются один раз, а не на каждый
запрос. Проверки `_load` используют уже загруженные модели. Профиль balanced может
выгружать ресурсы после 10 минут бездействия; это не происходит после каждой команды.
Синтез и STT выполняются существующими рабочими потоками, сетевые вызовы асинхронны.

### Реальные измерения, без микрофона и воспроизведения

Две серии по два одинаковых нейтральных API-запроса, до/после изменения кода:

- Первый непустой текст LLM: **20,86 / 19,60 с → 8,26 / 9,09 с**.
  Среднее: **20,23 → 8,68 с**.
- Полное завершение LLM: **22,13 / 20,90 с → 8,38 / 9,19 с**.
  Среднее: **21,52 → 8,79 с**.
- В серии «до» оба раза ответила Ollama `qwen3:8b`. В основной серии «после»
  оба раза ответила Gemini, фактическая версия **gemini-3.6-flash** через настроенный
  резервный идентификатор `gemini-3.5-flash`. Первая попытка остановилась около 6 с.
- Простая локальная команда времени: **1,56 / 1,46 мс → 1,79 / 0,78 мс**.
  Это обычный разброс очень малого времени, отдельного доказанного ускорения тут нет.
- Повторный локальный синтез Silero: **21,0 → 21,8 мс**, практически без изменения.
  Загрузка/прогрев в отдельных процессах: **2,55 → 2,69 с**, не время каждого ответа.

Отдельная серия с **одним** SDK-клиентом, как в voice: первый запрос дал текст
Gemini через **8,63 с**. Второй пропустил primary из-за cooldown, но резервная
Gemini вернула **429**; ответила Ollama через **9,21 с**, полное время **10,51 с**.
Таким образом, одинаковую задержку каждого запроса гарантировать нельзя: доступность,
квоты и нагрузка меняются. Никакой Billing не подключался, ограничения не обходились.

Оба настроенных ID дополнительно проверены read-only `models.get()` официального
Google SDK: существуют и поддерживают generateContent. Поэтому таймауты сами по себе
не объявляются доказательством несуществующей модели. Метаданные сохранены отдельно.

STT измерен на уже готовом синтетическом `mixed.wav` длиной **6,95 с**, без записи
пользователя: прогрев **1,80 с**, два распознавания **0,589 / 0,587 с**. Это проверка
скорости текущего `mlx-whisper large-v3-turbo`, не оценка качества живой речи и не
парное измерение STT до/после: распознаватель не менялся. Модели не скачивались
(`HF_HUB_OFFLINE=1`), текст распознавания в отчёт не записан.

**Граница измерений:** приведённые 20,23 → 8,68 с относятся к первому тексту API.
Это не измеренное время от конца реальной речи пользователя до первого звука.
Последнее доступно в штатной голосовой диагностике, но микрофон и акустический
вывод здесь не включались. Это малые реальные выборки с разными фактически
ответившими провайдерами, а не изолированный эксперимент только со streaming.

Санитизированные исходные результаты: [diagnostics/dialogue-latency](diagnostics/dialogue-latency).
Они содержат времена/модели/статусы, без ключей, частной истории и текстов ответов.

Повторяемые безопасные команды из корня проекта:

```sh
.venv/bin/python -m backend latency-check --live --stream --tts --runs 2 --label sample
HF_HUB_OFFLINE=1 .venv/bin/python -m backend latency-check --stt-file docs/audio/tts-regression/mixed.wav --runs 2
```

`--live` явно отправляет нейтральные запросы модели; `--tts` синтезирует только в RAM;
`--stt-file` читает только явно указанный mono PCM16 WAV до 30 секунд. Ни один из
этих флагов не открывает микрофон и не воспроизводит звук. `--label` лишь помечает
отчёт, не переключает версию реализации на старую.

Frontend: **10 тестов**, TypeScript и production build — успешно. Нативный

Новые регрессии проверяют многошаговый диалог, положительные/неоднозначные ответы,

## Ручная проверка

Перезапусти Чушпана обычным способом, чтобы применился Python-код. При ручном запуске
можно использовать `.venv/bin/python -m backend voice --no-briefing`, без второго
экземпляра поверх работающего приложения.

После проверки разрешений Safari проверь фразу «Открой мой любимый плейлист».
Если возникает именно предложение посмотреть доступные плейлисты, ответь
«Давай, посмотри». Должен вернуться фактический список без запуска музыки.
Без доступного Safari список также может завершиться честной ошибкой разрешений.
Не подтверждай ночной сценарий ради этого теста.

Проверь следующий вопрос в активной голосовой сессии, затем после закрытия окна
прослушивания с новым wake-word. Разговор в «Истории» должен остаться тем же.
После перезапуска сохранённая история также должна возобновиться; `/new` отдельно
создаёт новую. Для реального iPhone нужно проверить выдачу общей доверенной сессии
в его входном приложении; один переданный device_id этого не обеспечивает.
